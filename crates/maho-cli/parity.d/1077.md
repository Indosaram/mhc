Plan Todo 1077 aligns native in-process child session lifecycle (`dispose`, `steer`, `follow_up`) with pinned non-blocking execution semantics.

## Details
In pinned upstream `packages/senpi-task/src/runners/in-process/child-handle.ts:224-229`, `ChildSession.dispose()` is synchronous (`dispose(): void`) and fire-and-forget:
```ts
dispose: () => {
  if (disposed) return
  disposed = true
  unsubscribeObserver()
  session.dispose()
}
```
Likewise, senpi `AgentSession.dispose(): void` (`packages/coding-agent/src/core/agent-session.ts:2931`) executes synchronously without awaiting.

In native `crates/maho-cli/src/cli/task_session.rs`, `NativeChild::dispose` previously executed `self.executor.block_on(...)` synchronously. When a child task completed and the parent session underwent termination/shutdown on the main thread driving tokio's `new_current_thread` runtime, calling `block_on` from within an active runtime thread panicked with exit code 101 (`Cannot start a runtime from within a runtime`). Because `mhc` main uses `tokio::runtime::Builder::new_current_thread()`, `tokio::task::block_in_place` is unavailable (`block_in_place` panics on `current_thread`).

The bounded fix checks `tokio::runtime::Handle::try_current().is_ok()`:
- When invoked on a runtime thread, `dispose`, `steer`, and `follow_up` spawn the asynchronous operation onto `self.executor` without blocking, preserving the pinned fire-and-forget / queued semantics.
- When invoked off-runtime (e.g. from dedicated worker threads or tests), `self.executor.block_on` continues to run to completion.
- `prompt` remains driven synchronously via `block_on` since `senpi-task` guarantees `ChildSession::prompt` is exclusively invoked on a dedicated OS thread (`std::thread::spawn` in `InProcessChildHandle::begin_turn`).
