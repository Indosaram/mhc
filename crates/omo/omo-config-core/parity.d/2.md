# omo-config-core — TypeScript → Rust parity

Port of `@oh-my-opencode/omo-config-core` (75 `.ts` files: 43 source + 32 test files) to the Rust
crate `omo-config-core`. This file maps every TypeScript test file to the Rust test(s) that cover
it, or records `N/A` with the one-line reason.

Counts are recorded at the bottom of this file and are re-measured with
`cargo test -p omo-config-core -- --list` plus the source-file inventory of the reference package.

## Porting decisions that affect how the tests were translated

1. **Config content is `serde_json::Value`, not a typed struct tree.** The TypeScript package treats a
   parsed config as a plain record: the loader deep-merges records, the writer edits document paths,
   the migration engine moves documents around. Porting that content into ~60 serde structs would
   have created a second source of truth for the JSON contract (the `.jsonc` files are the contract)
   and would still not express zod's issue codes. Structural typing is therefore kept at the JSON
   boundary; Rust types are used for the crate's own API surface (options, results, diagnostics,
   errors, ports).
2. **The zod schema tree is ported as a schema tree** (`src/internal/validate.rs`), because the tests
   assert zod-specific issue data: `unrecognized_keys` with its `keys` list, `custom` refinements, and
   document paths such as `dag.max_nodes_per_run`. `safe_parse` returns the normalized document
   (defaults materialized, legacy aliases folded) or the issue list.
3. **Injectable ports became traits.** `OmoConfigReadFileSystem`, `OmoConfigWriteFileSystem`,
   `MigrationFileSystem`, `MigrationClock`, process liveness, and the target-writer hook. The default
   implementations use `std::fs`, `jiff::Timestamp` and `uuid`, so the Rust port keeps the
   "all IO goes through an injectable port" property the package advertises.
4. **Two test-only injection points were added** where Bun uses process-level test control:
   `UpdateOmoConfigOptions::timestamp` (the `setSystemTime` case in `writer.test.ts`) and
   `MockBoundary`/`on_boundary` returning `Result` instead of throwing (the crash-injection cases in
   `recovery.test.ts`, `batch.test.ts`, `transaction.test.ts`). Behaviour is unchanged; only the
   injection surface is idiomatic Rust.
5. **Dependencies.** No crate was added: `jiff` (timestamps), `serde`/`serde_json` (documents),
   `uuid` (atomic-write temp names) were already declared with versions from this workspace's
   `Cargo.lock`; `uuid` gained the pre-existing `v4` feature so `Uuid::new_v4()` matches the
   reference's `randomUUID()` temp-name generation. `tempfile` is the only dev-dependency.

## Known divergences (measured, not silent skips)

- **Empty or whitespace-only config document**: the reference's `jsonc-parser` returns `undefined`
  with no parse errors, so the package reports a `validation` diagnostic (`root must be an object`).
  The Rust JSONC engine reports the document as a parse error, so the same input yields a `parse`
  diagnostic. Both refuse the layer; no reference test covers this input.
- **`OmoConfigWriteError`/migration errors are returned, not thrown.** The messages are byte-compatible
  (`Failed to {operation} omo config at {path}: {detail}`, `Migration validation failed for {path}: ...`).
- **Callbacks return `Result` instead of throwing** (`onBoundary`, `writeTarget`, `transform`); the
  crash-injection tests assert on the returned error's text, which is the same text the reference
  asserts with `toThrow`.
- **`messages`/`causes` of wrapped filesystem errors**: the Rust port keeps an `FsErrorKind`
  (`Exists`/`NotFound`/`CrossDevice`/`Other`) instead of matching `error.code` strings, which is what
  the reference's `isFileExistsError`/`isFileMissingError`/`isCrossDeviceError` helpers actually test.
