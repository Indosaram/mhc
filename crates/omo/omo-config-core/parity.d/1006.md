## U-U10 published schema

`tests/schema_json.rs` is machine-consumed field equality, not prose: it asserts the emitted
`properties` key set equals `object_property_keys` of the corresponding schema node for the root,
layer, profile, `[native]`/`[senpi]`/`[codex]`, `computer`, `git_master`, `formatOnMutation`, `memory`,
`memory.recall`, `memory.recall.event_caps`, `memory.write_notice` and the model profile; that every
property carrying a `default` is absent from `required`; and that the documented default values and
`additionalProperties: false` survive. Generated-output execution (writing the asset) waits at the
global authoring barrier.

Divergence: upstream replaces the `[opencode]` property with a `$ref` to an embedded
`create[OMC]JsonSchema()` definition. The native `[opencode]` node is `record(any())`, so the emitted
property is `{"type":"object"}`; the richer OpenCode definition belongs to the omo-opencode config
schema, which is not ported here.

## Cross-owner compat

`resolve_omo_git_master_settings(&serde_json::Value) -> serde_json::Value` is the exact signature the
git-master producer requires (`.omo/authoring/git-master.md` in its worktree): infallible, always
returning both `commit_footer` (`false | true | string`) and `include_co_authored_by`. It is
re-exported at the **crate root** by an explicit `pub use schema::git_master::{…}` in `src/lib.rs`
(in addition to `pub use schema::*` and `pub use git_master::*` in `schema/mod.rs`), so the producer's
`use omo_config_core::{LoadOmoConfigOptions, OmoConfigEnv, resolve_omo_git_master_settings};`
resolves without relying on glob transitivity. The model-profile producer reads only the resolved
`model_profile` string and `model_profiles` record; the field and enum names match its reader.

## Known divergences (measured, not silent skips)

- U-U6 surgical pruning is ported (`loader/prune_invalid_leaves.rs`, `loader/layer_validation.rs`,
  `loader/loader.rs`). Three upstream `loader-prune-paths.test.ts` rows stay N/A because the native
  schema kernel reports a failing `Node::Union` as one `invalid_union` issue at the union path with no
  per-branch child issues, so a team-member field error (`teams.alpha.members.0.color` / `.bogus`)
  prunes the whole member instead of the single field; the layer-level, object-field-level,
  array-element and merged-config pruning cases are ported. The native task schema also stays pinned
  (no `host_engine_policy` / `process_runner` / `host_*` keys), so `task.host_engine_policy` is an
  unknown key for the native loader rather than an invalid value; the ported fixtures use native-known
  fields (`task.max_depth`, `task.default_concurrency`, `agents.*.temperature`,
  `categories.*.maxTokens`). The native port also renders the user config directory as `~/.maho` per
  the workspace config-home convention.
- `[senpi]` stays an accepted explicit key (as upstream keeps both `[native]` and `[senpi]`), and the
  loader canonicalizes it to `[native]` before the view merge, emitting one `deprecated-keys`
  diagnostic per layer that carried it.
- `[codex]`/`[native]`/`[senpi]` blocks no longer accept `codegraph`, matching the latest typed-harness
  schema. A layer carrying it is rejected whole by the native loader (the U-U6 gap), whereas upstream
  strips the unknown key with an `unknown-keys` diagnostic.
