Native registration is a real `EventKind::ToolResult` hook (`ExtensionApi::on`), not an export-only
stub: it matches upstream `asGitMasterReadResultEvent` (a successful `read` whose normalized
`file_path`/`path` ends with `/git-master/SKILL.md`), appends the directive after the existing
content, and leaves errors, other tools, other files and non-`tool_result` events untouched. The
component checks no disabled flag, matching upstream `git-master/index.ts` (unlike
`todo-fanout-reminder`).

The default settings loader consumes the config owner's API:
`GitMasterSettings::from_resolved(&omo_config_core::resolve_omo_git_master_settings(
&load_senpi_omo_config(LoadOmoConfigOptions { cwd, env }).config))` - upstream
`resolveOmoGitMasterSettings(loadSenpiOmoConfig({ cwd }).config)`. The crate never re-implements
the loader or the resolver.

Prose: the directive text is copied from `directive.ts` verbatim and carries no prose-pinning test;
only the machine-consumed footer value (the string that lands in user commit bodies), the
`commit_footer` union arms, and the no-`Co-authored-by`-trailer contract are asserted. This crate
ships no asset, so there is no shipped-copy equality to guard here (the `git-master/SKILL.md`
asset belongs to the bundled-skills lane).

Deviation N/A reason: upstream options are `loadSettings?: (cwd) => OmoGitMasterSettings`; the
native options add `env: Option<OmoConfigEnv>` as the deterministic seam for the default loader
(the `SenpiTelemetryOptions.env` / `ConfigStartupComponent::load_config` pattern). Production
leaves it `None`, so `load_senpi_omo_config` reads the process environment exactly as upstream's
`loadSenpiOmoConfig({ cwd })` does.
