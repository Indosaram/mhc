Native registration is a real `EventKind::SessionStart` hook (`ExtensionApi::on`), not an
export-only stub: it gates on mode (`tui` skipped), reason (`startup`/`new` only) and
`initial_model_provenance` (`cli`/`scoped`/absent yield), dedups per session id, resolves the
profile through [`src/resolve.rs`], walks the auth-failure tier through
[`src/request_auth.rs`] + [`src/credential_policy.rs`], applies through the SESSION-ONLY
`set_session_model` / `set_session_model_thinking_level` (never the persisting setter, so no
`settings.json` is written), and emits `omo-model-profile:applied` / `:unavailable` / `:unknown`
notices. It listens to no other event.

The default config loader consumes the config owner's API
(`load_senpi_omo_config` + the resolved `model_profile` / `model_profiles` JSON); the schema and the
loader are never re-implemented here.

Prose: the notice text ([`src/notice.rs`]) and the directive-free model chain table are shipped
copies of the pinned source and carry NO wording-pinning tests. Only machine-consumed values are
asserted: the custom-type tokens, `display`, the `details` fields (`profile`, `model`, `reasoning`,
`skipped`, `authFailed`), the selected registry model, the session thinking level, the registry call
order, and the redaction of raw error text. `chain-provider-ids.test.ts` carries the shipped-copy
equality it is: the engine id set is a const here because the native side has no
`builtinProviders()` accessor (see the seam below); the check still fails on a typo'd id.

## Deviations (N/A reasons)

1. Upstream options are `loadConfig?: typeof loadSenpiOmoConfig`; the native options add
   `env: Option<OmoConfigEnv>` as the deterministic seam for the default loader (the
   `SenpiTelemetryOptions.env` / `GitMasterAttributionComponentOptions.env` pattern). Production
   leaves it `None`, so `load_senpi_omo_config` reads the process environment exactly as upstream's
   `loadSenpiOmoConfig({ cwd })` does.
2. Upstream `extractRegistry` returns `undefined` for a host without `modelRegistry`; the native
   `ExtensionContext.model_registry` is always present, so that branch has no counterpart. Upstream's
   `runtime === undefined` probe guard is likewise absent: the native registry always exposes the
   probe port.
3. `errorKind` is upstream `${error.name}/${error.code}`, read from the typed
   `ExtensionFailure::class`/`::code` on the shared port; the message is NEVER inspected, so a message
   whose leading token is key material cannot leak into `errorKind`. Outstanding: senpi's
   `sanitizedAuthErrorDetail` walks the `error.cause` chain (up to 4 links, joined with ` <- `) so a
   wrapped `OAuthRefreshExchangeError` keeps its class name; `ExtensionFailure` has no `cause` field
   yet, so the native detail reports the top failure only (`.omo/authoring/model-profile.md`).
4. The rung matcher calls `model_core::fuzzy_match_model` +
   `model_core::transform_model_for_provider` directly instead of
   `delegate_core::resolve_model_for_delegate_task`, because that native port has no
   `allow_unlisted_providers` field and runs its cross-provider branch unconditionally, where the
   pinned TS gates it on `input.allowUnlistedProviders !== true -> continue`; its `candidateIds`
   both-spellings logic is also absent. Matching semantics are otherwise the pinned single-rung warm
   branch.
5. The probe runs through the shared SLOT-AWARE overloads
   (`get_provider_auth_for_slot` / `get_api_key_and_headers_for_slot`) and the rotation policy reads
   `get_provider_auth_status` directly; exact required signatures and caller paths are in
   `.omo/authoring/model-profile.md` section 2. There is NO flat-slot fallback and no injected
   auth-status stub in the component, and this crate declares NO auth-status type (the trait's return
   type is the SHARED ext-api type; a component-local one would be an ext-api -> component cycle).
   The upstream credential-POOL cases (flat-expired-but-sibling-valid, pinned-pool, rotation-off-pool,
   runtime-key) are exercised through the real `register` hook, asserting the per-slot call order and
   the resolved slot threaded into the model scope. The runtime-key case is proven only at the
   COMPONENT boundary (a registry reporting `source: "runtime"`); the host must map a real runtime API
   key onto that source. The crate does not compile until host owner `dag_f53d3c3c` lands the shared
   surface; the other request-auth cases (provider scope, model scope, slots enumeration, rotation
   policy, redaction) are exact.

6. `models-json.ts` returns the identical parsed object on a cache hit upstream
   (`expect(readModelsJson(dir)).toBe(first)`); the native cache hands the parse out behind an `Arc`
   and the test asserts `Arc::ptr_eq`, which is the same identity claim. A file that exists but does
   not parse is cached as JSON `null` exactly as `readJsoncFile` answers `null`.
7. `describe.ts` has no upstream unit test of its own; its view-state branches are specified by the
   implementation, and the one integration assertion (`omo-native` `model-chains.test.ts`, default
   selection + applied selector + exclusion from the resolver) is ported to `tests/describe.rs`
   together with the remaining branches. The native module is the pure projection only: the
   `omo doctor --models` command that renders it belongs to the omo-native lane.
8. `exclude_models` matching itself lives in its own upstream file
   (`omo-config-core/src/models/excluded-models.ts`), so it is ported to
   `omo_config_core::models::excluded_models` and imported here rather than re-implemented in the
   component (see the omo-19 report's CROSS-CRATE note).
