## Bounded adaptations (no behavioral improvement)

- **`AutocompleteItemLike.awaitsArguments` is not mirrored.** The native
  `maho_tui::autocomplete::AutocompleteItem` has no such field
  (`crates/maho-tui/src/autocomplete.rs:19-23`; the awaits-arguments concept lives on
  `CommandSpec::argument_hint`, owned by `maho-tui`, outside this lane's write scope). The native
  alias mirrors the skill row's `description` only; `tests/autocomplete.rs` asserts the mirrored
  description instead of the flag.
- **`readInputEvent` / `readUi` payload guards are not reimplemented.** Native dispatch is typed
  (`ExtensionEvent::Input`, `ctx.ui`), so `payload.type === "input"`, `typeof text === "string"` and
  `eventCtx.ui` have no native counterpart. The `source === "extension"` guard **is** preserved, and
  the warning is gated on `ctx.has_ui` (upstream `readUi(eventCtx)?.notify?.()`), while the
  `handled` result is returned unconditionally.
- **`readBundledSkillNames` returns `io::Result`.** Upstream throws when an existing directory
  cannot be listed; the native `Extension::register` cannot return an error, so the port surfaces
  the failure and aborts registration with a logged diagnostic instead of silently registering
  nothing (no silent swallow, no fallback).
- **The host-command lookup is the captured runtime.** `pi.getCommands?.()` maps to
  `runtime.session_actions()?.get_commands()` on the `ExtensionRuntime` cloned from `api` at
  registration (no `ExtensionContext` accessor exists, and none was invented); an unavailable
  session-action binding is upstream's `getCommands === undefined` (rewrite unconditionally), while a
  failing `get_commands()` propagates out of the input handler exactly as the upstream throw does.
- **The warning is asserted by the skill name, not by its prose.** `tests/skill_commands.rs` asserts
  one `Warning` notice that contains the skill name (the machine-consumed identifier) rather than
  pinning the sentence, per AGENTS.md's prose-pinning rule.

## Asset- and registry-dependent rows (cases 1-2)

`tests/argument_hints.rs` and `tests/documented_commands.rs` read the SELECTED packaging overlay
(`assets/omo-latest/skills` + `manifest.json`, overridable with `MAHO_OMO_LATEST_SKILLS_ROOT`) and
the repo `README.md`; a missing overlay or README fails the test loudly (no skip, no synthetic
substitute). Staging the overlay is the packaging lane's deliverable (contracts/interfaces.md
L-IF-2) and must be present at the global gate.

`documented_commands.rs` resolves the known set from real registries only: native discovery over
the overlay, `maho_core::slash_commands::builtin_slash_commands()`, and the omo components' own
registration API (`maho_omo_task::commands::register_task_commands`,
`maho_omo_task::dag_commands::register_dag_commands`,
`maho_omo_memory::commands::register::register_memory_commands` registered into a real
`ExtensionApi` and read back from `api.registered.commands`). No command name is hardcoded, so a
registration that disappears fails the test. Bounded gaps, each recorded rather than papered over:

- Upstream also scrapes the engine's builtin **extensions** (`registerCommand(...)` under the senpi
dist's `core/extensions/builtin`), e.g. `goal`. Native builtin extensions live in
`crates/builtins/maho-ext-*` and are registered at assembly by the builtins lane; this crate cannot
construct that registry, and no command documented in the scanned surface comes from it.
- Upstream scans `docs/guide/overview.md` and `docs/guide/orchestration.md`; the native repo ships
no `docs/guide/`. Their only extra documented command is `/search` (memory's, registered above but
not asserted here).
- Upstream's `computer-use` (`computer`) and `memory/palace` (`palace`) owners have no native crate
yet, so their commands cannot be registered here.

## Pending cross-lane dependency (recorded, not duplicated)

This crate resolves the bundled skills root through `maho_omo_bundled_skills::resolve_bundled_skills_dir`
and builds its host-command view through `maho_omo_bundled_skills::host_commands_from_runtime`, so it
inherits that crate's config-lane dependency (`collect_disabled_skills`, contract U-L8, delivered by
the config lane with the by-ref receiver; the config crate must be integrated before either crate
compiles). It performs no config read itself, defines no fallback, and reads the command registry
only through `ExtensionRuntime::session_actions()`, which the host binds.
