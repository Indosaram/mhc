## Notes

The prior hand-rolled `compile_expression`/`safe_star_repeat`/`risky_simple_repeat`/
`normalize_literal_braces` approximation is replaced by a structural port of the pinned picomatch
parser (`constants`, `utils`, `scan`, `parse`, `picomatch` glue), so extglobs, brace expansion and
ranges, quoting, POSIX classes, `bash:true` globstar/star, negation and JS UTF-16 unit matching are
derived from the parser rather than patched case-by-case.

Final proof is the **source-generated** corpus (`tools/golden/latest-omo-rules-matcher.mjs`, gated by
`tools/golden/latest-omo-rules-pin.mjs`) emitted from the pinned picomatch at the final gate; the
357-case `tests/matcher-source.json` matrix and the authored grammar assertions are bounded
differential evidence only. The corpus and the source hash manifest are **not** committed by this
authoring pass: the generator must run before the acceptance gate (see `authoring/rules.md`).

`MatcherError` now carries `EmptyPattern`/`Syntax`; the two source error strings
(`Expected pattern to be a non-empty string`, `Input length: N, exceeds maximum allowed length: 65536`)
are preserved exactly. Full pattern-language parity is a structural claim, not a finite-corpus
claim.

## UTF-16 unit domain (todo 1005, revision 2)

The parser now maps the pattern through `utils::js_units` before tokenizing (`Parser::new` and
`parse::fastpaths`), exactly as `Compiled::is_match` already mapped the haystack. Pinned picomatch
measures strings with `String#length` — UTF-16 code units — in `analyzeRepeatedExtglob`
(`literal.length === 1`), `getStarExtglobSequenceChars` (`branch.length !== 1`) and
`hasRepeatedCharPrefixOverlap` (`a[0]`, `char.repeat(a.length)`), and the port's `Vec<char>` is now
that same unit vector, so an astral branch is never treated as a single-character branch. The
regex source is emitted in the same domain and `js_regex_expression` drops a `\` written before a
unit character (JS identity escape; the Rust engine rejects `\` before a non-ASCII character).

## JS escape semantics and `expandRange` sort (todo 1005, revision 3)

`js_regex_expression` now translates every backslash escape to the JS (Annex B, no `u` flag)
meaning instead of passing it through. `regex-syntax` disagrees with JS on the ASCII surface:
`\a` is the bell (JS: literal `a`), `\z`/`\A` are text anchors (JS: literal `z`/`A`),
`\<`/`\>` are word-boundary assertions (JS: literal `<`/`>`), `\U` is hex (JS: literal `U`),
`\p`/`\P` are Unicode classes (JS: literal `p`/`P` without the `u` flag), `\0`..`\9` are
unsupported backreferences (JS: legacy octal / identity) and any other escaped ASCII letter is a
parse error (JS: identity). The port emits the shared class/control escapes verbatim, `\xHH`
verbatim, `\uHHHH` as `\u{HHHH}`, a JS `LegacyOctalEscapeSequence` (`\0`..`\377`) and `\cX` as
`\x{..}`, and every JS identity escape as the literal character. The pinned `normalizeGlobs`
rewrites every `\` to `/` before a glob reaches picomatch, so this behavior is observable only
through the grammar module; `tests/matcher.rs` drives it there and `grammarCases` in the
source-generated corpus covers it.

`expand_range` now sorts with `Array#sort`'s default comparator (UTF-16 code-unit order) instead of
Rust's scalar-value order, and emits the class body in the mapped unit domain: each UTF-16 unit
range is split into the mapped pieces (`0xD800..=0xDFFF` maps to `0x1D800..=0x1DFFF`), and an
out-of-order range takes the pinned `escapeRegex`/`join('..')` fallback exactly as `new RegExp`
throwing does. The pinned `new RegExp(value)` validity check is mirrored by `translate_unit_class`
(`UnitClass::OutOfOrder`), and bodies carrying a JS class escape (`\d`, `\w`, ...) keep the pinned
template plus the Rust validity check (`UnitClass::Unsupported`).
