## Branch layout (deviation from plan todo 16)

The plan asked for one `sync5152/mit-<unit>` branch per unit. Instead, every clean-tree commit
was cherry-picked, in order, onto a single branch, `sync5152/mit` (head `6790cbb1f`). That branch
was merged into `sync/omo-5.1.52` as `d4390d8e3` ("merge(sync-5152): mit"). The per-unit commits
stay separate on that branch, one or more per unit, as listed in the table above.

Paths touched by `sync5152/mit` (`31bad7b00..6790cbb1f`): only `crates/maho-*` MIT crates and
their `PROVENANCE.md`, plus one path outside `crates/maho-*`:
`crates/builtins/maho-ext-recommended-models` (`src/lib.rs` and a new `PROVENANCE.md`), from
`faad80a8` (unit model-selection-5152-d6). A grep for
`ultrawork|ulw|boulder|Sisyphus|Kibitzer` over every changed file of the branch finds nothing.

### `maho-ext-recommended-models`

- What changed and where it came from: the D6 spec states a data prerequisite. The Kimi entry of
  the recommended data becomes `kimi-k3.1-pro` at `max`, ranked `kimi-coding`,
  `kimi-for-coding`, `moonshotai`, `opencode-go`. That is the MIT senpi v2026.10.27-2 data,
  which the MIT-direct lane builtins-b ports file-for-file (census row senpi-builtins-b-05,
  commit `874b62223`, follow-up `0c14b7a33`). The D6 implementer made the same data change in
  the clean tree from the spec text (`ba5600a`, cherry-picked as `faad80a8`). It changed two
  data lines in `src/lib.rs` and added a `PROVENANCE.md`.
- What the merged tree keeps: builtins-b was merged into `sync/omo-5.1.52` (`20024a1e2`) before
  `sync5152/mit`. In the `mit` merge (`d4390d8e3`) the conflict in
  `crates/builtins/maho-ext-recommended-models/src/lib.rs` was resolved to the builtins-b side.
  The file is byte-identical to the merge's first parent. The only file of that crate that the
  merge took from `sync5152/mit` is `PROVENANCE.md`.
- Did anything in that crate come from the clean-room implementer? No code or data. The data in
  `src/lib.rs` is the MIT-direct senpi port. The clean-room edit to it was discarded at the
  merge. Its content was identical in effect: same id, level and provider order. The clean-room
  `PROVENANCE.md` that the merge kept describes that discarded edit. On the merged tree it should
  instead say that the data is the senpi port (method P, builtins-b) and that the clean-room D6
  change was superseded. That PROVENANCE edit belongs to the integration branch, not to this
  spec branch; it is listed for todo 19.
